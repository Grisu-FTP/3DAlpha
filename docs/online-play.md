# Playing over the internet: AlphaComputer, and this console's half of it

Two 3DS consoles in one room find each other with a beacon on the local radio
(`platform/ctr/local_link.hpp`). Two consoles in different countries cannot, and
asking a player to forward a port is the thing this feature exists to avoid. So
there is a small server — [AlphaComputer](../../AlphaComputer), a sibling
repository — whose entire job is to introduce them.

**It never holds a world.** No chunk, block or entity is parsed there; the
largest message it handles is a list of open sessions. Once the two consoles
have been introduced they talk to each other directly, and the session that runs
between them is `core/net/session.hpp` — the same handshake, the same world
server, the same terrain sharing that two consoles in a room run. What changed
underneath it is only what the frames travel on.

**One thing has run on a 3DS**, and it failed: the bind, below. Nothing past it
has — no login from a console, no punch between two of them, no session.

## Why the console has a key

The question is whether a friend code can be verified on a modded 3DS so that
nobody can pretend to be somebody else. It cannot — not cryptographically, and
not by any route the console exposes. Three things were checked against the
headers on this machine rather than assumed:

| Fact | Where | Consequence |
|---|---|---|
| `FRD_PrincipalIdToFriendCode` and `FRD_FriendCodeToPrincipalId` are a pure reversible pair | `frd.h` | A friend code is a 32-bit principal ID plus a check byte. Anyone can compute a valid one for any ID. |
| `PS_SignRsaSha256(hash, ctx, sig)` takes a **caller-supplied** context | `ps.h` | It signs with a key you hand it. It attests to nothing. |
| `PS_GetLocalFriendCodeSeed`, `PS_GetDeviceId` return console-unique **values** | `ps.h` | Readable secrets, not signing oracles. |

And the decisive one: the homebrew is ours and the console is modded, so
whatever check we write, the person running it can patch out.

So identity is **staked, not proved**. The first console to claim an identity
binds an Ed25519 public key to it; every login afterwards signs a nonce the
server chose, and a console offering a different key is refused.

```
first contact   claim 3ds:000123456789 + ed25519 public key   ->  bound, owned
every login     sign(domain || len || identity || nonce)      ->  verified
wrong key                                                     ->  refused
```

The residual risk — squatting an identity whose owner has never connected — is
real, bounded, and written down in AlphaComputer's `docs/identity.md`.

### Where the key lives

`sdmc:/3dalpha/identity.key`: 32 raw bytes and nothing else. No header, no
version, no checksum — a file whose whole contents are the secret is one a
player can back up, move or destroy without being told how, and a format with a
header is a format with a migration.

**The key file is the account.** Delete it and this console is a stranger again;
copy it to another console and that console is this player. Both are
consequences worth knowing rather than bugs.

A file of the wrong length is **refused, never overwritten**: replacing it would
take this console's identity away for good, and recovery is deliberately an
out-of-band step an operator performs.

### The identity string

`3ds:` and twelve decimal digits — the friend code, which is
`(sha1(principalLE)[0] >> 1) << 32 | principal`. The principal ID comes from
`FRD_GetMyFriendKey`; when the friend service was never set up, and it often was
not, the device ID stands in. That is a different number about the same console:
stable, console-unique, and readable without the friend service. It risks
colliding with a real friend code's principal, which would show up as an
identity already claimed — the same failure this design already has a story for,
and rarer than the number of consoles with no friend account at all.

### The crypto is ours

There is no Ed25519 in libctru, in zlib or in anything else this build links, so
`core/util/ed25519.cpp`, `core/util/sha512.cpp` and `core/util/sha1.cpp` are
written from their specifications. Nothing is vendored and nothing is owed a
notice.

The field is 2<sup>255</sup>−19 in eight 32-bit limbs with 64-bit products — an
ARM11 has no 128-bit integer, which rules out the usual radix-2<sup>51</sup>
form, and plain schoolbook is *fewer* multiplies than the classic
radix-2<sup>25.5</sup> one and far easier to be sure of. The curve arithmetic is
the unified extended-coordinate addition law, used for doubling as well, because
completeness is worth more than the few multiplications a dedicated doubling
saves. Scalar reduction mod L is a bitwise double-and-add rather than the
reference implementation's unrolled routine: five hundred iterations of a shift
and a conditional subtract, microseconds once per signature, and short enough to
read.

**Nothing in it is constant-time and nothing needs to be.** A signature is
produced on a console nobody else is running code on, against a server that sees
only the result.

`tests/crypto_test.cpp` checks all of it against OpenSSL — an implementation that
did not come from the same head that wrote this one.

## The protocol

Big-endian, one message per UDP datagram, four bytes of `ACMP` in front.
`core/net/ac_wire.hpp` is the codec and AlphaComputer's `src/wire/` is the other
half; `kProtocol` is checked at `Hello` before any later field is interpreted,
so two builds that disagree stop rather than misreading each other.

```
C -> S  0x01 Hello            u16 protocol, string identity, [32] public_key
S -> C  0x02 Challenge        [32] nonce, addr reflexive
C -> S  0x03 Auth             [64] signature, opt<string> platform_name
S -> C  0x04 AuthOk           [16] token, string display_name, opt<string> handle,
                              bool first_claim, string key_fingerprint,
                              u16 transfer_port
        0x05 AuthFail         string reason
C -> S  0x10 Keepalive        [16] token          (every 10 s)
S -> C  0x11 KeepaliveAck     addr reflexive
C -> S  0x20 HostSession      [16] token, string world, string game, u8 max,
                              bool locked, opt<addr> local
S -> C  0x21 SessionOpened    u64 id, string join_code
C -> S  0x22 CloseSession     [16] token
C -> S  0x24 ListSessions     [16] token, opt<string> game
S -> C  0x25 SessionList      u8 count, [SessionInfo; count]
C -> S  0x26 JoinRequest      [16] token, opt<string> code, u64 id, opt<addr> local
S -> C  0x27 PunchNow         u64 id, string peer_name, [Candidate], [16] punch_token,
                              u16 window_ms
C -> S  0x28 PunchResult      [16] token, u64 id, bool connected
S -> C  0x29 RelayAllocated   u64 id, addr relay, [16] token
C -> S  0x2A RequestLinkCode  [16] token
S -> C  0x2B LinkCode         string code, u16 expires_in_s
C -> S  0x2C Unlink           [16] token
S -> C  0x2D Unlinked         string display_name
S -> C  0xFF Error            string reason
```

`0x2C`/`0x2D` are protocol 2 and were added for this feature: before them the
only way off an account was the website, which a player holding a 3DS does not
necessarily have to hand. `transfer_port` is protocol 3, and is where world
sharing listens -- see below.

**Strings are plain UTF-8**, not Java's modified form — this is our protocol and
not Minecraft's — and they truncate on a character boundary, never splitting a
character, which is the bug the UDS beacon already hit once cutting Mii names.

The decoder faces the open internet: every read is bounds-checked, every failure
is a refusal, trailing bytes are refused, and **a list count never sizes an
allocation** before it is checked against a ceiling.

## Binding it, which a console refused

The first hardware run of the Profile screen died on **`bind(): Invalid argument
(errno 22)`**, and the cause is worth writing down because it is not guessable
from the BSD API libctru presents.

Disassembling `soc_bind.o` out of `libctru.a` shows where EINVAL can come from:
the only check in libctru's own wrapper is `addrlen`, against 8 for `AF_INET`
and 28 otherwise, and this call passes 16 with `sa_family == AF_INET == 2`. So
libctru was not refusing it — `SOCU:Bind` was, and `_net_convert_error` turned
the service's own code into an errno.

Two things differed from libctru's own sockets example
(`$DEVKITPRO/examples/3ds/network/sockets`), which binds successfully:

| This did | The example does |
|---|---|
| `INADDR_ANY` | `gethostid()`, the console's own address |
| port 0, for an ephemeral port | an explicit port |

Both are now handled. The bind address is the **platform's answer**, not a
default — `ctr::localAddress()` on a console, 0 on the host build, which is
where it means what a PC means by it. `gethostid()` cannot go in core, because
on Linux it returns a host identifier and not an address at all. The port is
asked for in order: 0 first, because every other platform answers that with an
ephemeral port, then a short list of fixed ones from the IANA dynamic range.
Which of the two a console actually objects to is not something a host can
determine, so both are offered rather than one being guessed at.

**`gethostid()` is also 0 before the console has joined a network**, and the
Profile screen is easy to open in that second. That is a reason to wait, not to
refuse: `Stage::WaitingForAddress` retries for ten seconds with "Waiting for
Wi-Fi..." on screen, and only then says to check the switch.

`tests/udp_socket_test.cpp` holds what a host can hold: that a bind which cannot
succeed is reported in words a player can act on rather than as an errno, that a
bound socket knows the address it will offer as a candidate, and that a datagram
crosses and says where it came from.

## One socket, and why

The public address a NAT hands out belongs to the *socket* that sent through it.
So the control messages, the punch probes and the game itself all leave by the
same door — a second socket would be a second mapping, and the address the
server reported would be for the wrong one.

`core/net/ac_link.hpp` is what sorts the three apart on the way back in:

| From | Is |
|---|---|
| the server's address | an `ACMP` message, handed to `ac::Client` |
| anywhere, 21 bytes, `ACPK` + a known punch token | a probe, answered here |
| the relay's address, 21 bytes, `ACPK` + the punch token | the other end's relay hello, swallowed |
| the relay's address | a game frame; the relay strips the token on the way out |
| any address that carried a peer's punch token | a game frame; replies go to the first such address |
| anything else | dropped, which on a public port is most of what arrives |

## Getting two consoles connected

### The punch, which is the normal path

A console learns its own public address for free — the server reports the source
it saw, refreshed on every `KeepaliveAck`. Knowing the *other* side's address is
not enough: most NATs forward an inbound datagram only from an address the host
has recently sent to. So both ends fire at roughly the same moment, and each
one's outbound probe opens the pinhole the other's inbound probe needs.

**Simultaneity is the entire mechanism**, which is why one `JoinRequest`
produces a `PunchNow` at *both* consoles with a shared token and a window they
count down together. Fired one-sidedly it works only on a full-cone NAT;
`a_punch_only_one_console_knows_about_does_not_get_through` is that case as a
test.

The probe itself is ours and the server has no opinion about it: `ACPK`, the
sixteen-byte shared token, and a byte saying whether this is the opening probe
or the answer. The full token is matched, so a probe from somebody who was never
introduced is dropped rather than becoming a peer.

**Either side reporting success is enough**, and it is reported the moment it is
true rather than at the end of the window: a punch is symmetric, so if this
console has the other's packets the path exists both ways.

The peer's address is **fixed once it answers**. A datagram from somewhere else
carries nothing that proves who sent it, so a NAT that rebinds mid-session ends
the session through the link's own timeout rather than being followed to an
address a stranger could have named.

### The local candidate

The server offers the peer's **local** address first, ahead of the public one.
Two consoles on the same wireless network should talk across the room rather
than out to the internet and back; many home routers will not hairpin that
traffic at all. `UdpSocket::open` works out which of this console's addresses to
offer by connecting a throwaway datagram socket at the server and reading back
what the routing table chose — no packet is sent, and a console with two
interfaces answers with the one that matters.

### The relay, for the connections that cannot be made

A symmetric NAT allocates a fresh external port per destination, so the address
the server observed is not the address the peer will see. There is no hole to
punch, and the only options are a relay or telling the player it cannot work.
Frames go out as `token || payload` and arrive with the token stripped.

**Each end says hello to the relay the moment it is allocated, and keeps saying
it until something comes back.** AlphaComputer's relay is never told where the
two consoles are: `Relay::handle` learns an end's address from the first datagram
carrying that end's token, and drops a datagram for an end it has not learned
yet. A host says nothing until a guest has, so without the hello the guest's
first frames were dropped and the host never registered at all -- the guest's
handshake ran out as "the host did not answer". The hello also opens the
console's own NAT to the relay, which is the server's machine on a port the login
never wrote to. It is a probe (`ACPK`, the punch token, "pong"), so the other end
swallows it rather than handing it to the session. It was checked against the
real Rust relay with `AC_FORCE_RELAY=1` (below): without it the join fails
exactly that way, and with it the session crosses, against a local server and
against `ac.grisu-ftp.de`.

**At most one relayed peer per session, and that is the server's limit rather
than this build's**: AlphaComputer keys relay allocations by session id, so a
second guest that could not punch would take the first one's allocation. A host
refuses the second relayed guest out loud instead of quietly breaking the guest
already playing.

## What the player sees

**Options → Profile** (`Screen::Profile`) is the whole account feature: the
server address, the status, what the server calls this console, and one button
that is *Link* when the console is not on an account and *Unlink* when it is.
Link asks for eight characters to type into the website; Unlink sends `0x2C`.

The server address is stored as the **website's URL** — `https://ac.grisu-ftp.de`
by default — because that is the form anybody publishes and the thing a player
types a link code into. The control plane is UDP 7717 on the same host and
appears in no URL, so the host name is taken from what was typed and the port is
the default unless the URL names one.

### Hosting: privacy, then a world, then a lobby

```
Multiplayer -> Host -> Internet -> Privacy -> a world -> the lobby -> START
```

**Privacy is asked before the world** (`Screen::OnlinePrivacy`), because the
answer is what the server is told when the session is registered and that
happens the instant the world is picked. It is remembered in `3ds.ini` as a
word — see `core/settings/online_privacy.hpp`.

| Answer | Means | Today |
|---|---|---|
| Code only | the six characters the host reads out are the way in | works |
| Friends only | this console's friends, and no code at all | refused |
| Friends and code | friends walk in; anybody else needs the code | refused |

**All three register the session unlisted.** A world on somebody's console is
not a public server, so `locked` is true whichever answer was given and what
differs is only who is handed the way in. The two friend answers are drawn
disabled and refused out loud: AlphaComputer stores friendships — they are made
on its website — but no message in protocol 2 asks a console for them and no
join is turned away on their account, so a session registered that way would be
one nobody could enter.

**The lobby** (`Screen::OnlineHost`) is where the session now begins rather than
where the code is shown on the way past. The join code is on the top screen at
the size a person reads across a table; **who has arrived is on the bottom one**,
on the dirt rather than on the console's text grid. START opens the world, B
closes the lobby and tells everybody in it why.

The list is people, not a promise: a guest who types the code while the host is
still looking at it is introduced, punched through, welcomed and listed. That
means **the session runs before the world exists** —

* `HostPlay::openLobby` opens the `HostSession` with no `WorldServer` behind it.
* The `GeneratorId` a guest checks its build against is read out of `level.dat`
  with `world::WorldPeek`, which takes no lock and rewrites nothing — the world
  is about to be opened for real, and `AnyStorage::open` would have claimed
  `session.lock`.
* `HostPlay::pumpLobby` carries it once a frame and **does not service the
  link**: `Menu::pumpOnline` is already doing that on the same socket.
* `HostPlay::startWorld` opens the world server when the world opens and hands
  it everybody the lobby already let in. Earlier would have stood them at
  0, 64, 0, which is what `ServerWorld::spawnPoint` answers with no streamer.
* `Menu::takeHost` gives the running session to `runHosted`, and `HostPlay::open`
  **adopts** it. Opening a second would drop every guest and reissue player ids.
* `runHosted` sends `Msg::Away` for twenty seconds first, because nothing pumps
  a session while a world is opening off a card.

### Joining: a code, and a friend list that is not here yet

**Multiplayer → Join → Internet** is `Screen::OnlineJoin`, and it is two rows:
**Enter Code**, and **Friend list**, disabled and labelled so. There is no
directory browser, because there is nothing for it to find — this build hosts
unlisted whichever privacy answer was given, so the six characters are the
invitation. `Client::listSessions` is still in the client and still tested; it
is simply not a row.

**A session can be joined after it has started.** The session stays registered
with the server, and a punch landing mid-game is handled inside `HostPlay::pump`
by the same `Connection` that handles one landing in the lobby.

## Sharing a world: Import and Export over the internet

**World Settings → Export → Internet** uploads a world and shows a six-character
code; **the world list's Import row → a name → Internet → the code** downloads
it. It is not `net::world_copy` over the relay, which moves a world in
`link::Msg` frames with no flow control of its own: AlphaComputer has a TCP port
for it (its `docs/transfer.md`), which this console finds from `AuthOk`'s
`transfer_port` -- the reason for protocol 3 -- and authenticates on with the
login's own token.

**The server holds the world without opening it**, so everything about what the
bytes are is ours, in `core/net/world_share`:

```
ACWT u16 1, then frames: u8 kind, u32 length, payload      (the server's)
zlib( "3DAW" u16 1  u32 files  u64 bytes
      { u16 length  path  u64 size  bytes } x files )     (ours, inside Data)
```

The receiving console holds the archive to the rules a copy over local wireless
is held to: `world::safeRelativePath` on every path, `world_transfer.hpp`'s size
limits, the declared counts checked against what arrived, nothing after the end,
and all of it in the `.importing` staging directory until `ImportStaging::commit`
agrees it is a world. The server never looked, so a hostile archive is the case
the tests spend the most on.

**Level 2 deflate, from a measurement.** On the real 1122-file a1.1.2 world
(1121 of the files gzip already): level 1 makes it **2.9% larger**, level 2 5.9%
smaller, 6 and 9 only 0.1% more for more time. Every download pays for the size
again. Not timed on an ARM11.

**The code is on screen before the upload finishes** -- the server hands it out
before the first byte -- and a download may start while the upload is running;
it follows it. **The share lives as long as the login**: the screen keeps
`Online` pumped while it is up, B withdraws the world (`Stop`, one round trip on
the worker), and a login that was replaced -- `ac::Client` logs in again on its
own after a long suspension -- shows "No longer shared".

**All of it runs on a `Net` worker** (`platform/ctr/online_share`): the walk,
the deflate, the inflate, the card writes and the blocking socket. The menu reads
atomics. The only wait on the main thread is the destructor's join, bounded by
the eight-second connect.

## Single player waits for none of it

**Nothing above exists in a single-player session.** `Menu::online_` is null
until `ensureOnline` is called, and it is called from exactly three places:
opening the Profile screen, choosing Internet on the multiplayer menu, and
choosing Internet for an Import or an Export.
Opening a world, playing one and saving one touch none of it, so a game that is
never played online opens no socket, looks up no name and waits no frames.

Two tests hold the line —
`a_client_that_was_never_begun_sends_nothing_and_waits_for_nothing` and
`a_connection_that_was_never_begun_is_inert` — and the one call that *would*
block, turning a host name into an address, runs on a worker with the screen
saying what it is doing.

## Testing

```sh
# The codec against the server's own bytes, and the state machine against them.
./build-host/3dalpha_tests ac_
./build-host/3dalpha_tests nat_that_only     # a punch through a modelled NAT
./build-host/3dalpha_tests falls_back_to_the_relay

# Regenerate the vectors when AlphaComputer's wire::PROTOCOL moves.
cd ../AlphaComputer && cargo run --example wire_vectors > ../3DAlpha/tests/ac_wire_vectors.hpp

# Against a real server. Two terminals.
./target/release/alphacomputer alphacomputer.toml
./build-host/3dalpha --online 127.0.0.1:7717 host          # prints JOINCODE
./build-host/3dalpha --online 127.0.0.1:7717 join <code>
./build-host/3dalpha --online 127.0.0.1:7717 profile       # asks for a link code
./build-host/3dalpha --online 127.0.0.1:7717 unlink

# World sharing. Export prints SHARECODE before its upload is done; import it in
# the other terminal, even mid-upload, then diff the two trees.
AC_SHARE_SECONDS=60 ./build-host/3dalpha --online 127.0.0.1:7717 export <copy of a world>
./build-host/3dalpha --online 127.0.0.1:7717 import <code> <saves dir> Imported
./build-host/3dalpha_tests every_transfer     # the ACWT frames against the server's bytes

# The relay path, which a PC's punch never needs. Both ends.
AC_FORCE_RELAY=1 ./build-host/3dalpha --online 127.0.0.1:7717 host
AC_FORCE_RELAY=1 ./build-host/3dalpha --online 127.0.0.1:7717 join <code>
```

`AC_FORCE_RELAY=1` drops every probe the harness would send straight to the other
console, so the punch fails and the server falls back to the relay.
`AC_TYPING_MS=8000` on `join` waits the way a console does -- two seconds of menu,
then the keyboard applet with nothing pumped -- before it sends the code.

**A request is timed from when it is sent.** A console joins long after it logged
in, and `Client::queue` used to start the request on the time the login went out,
so a join typed more than six seconds later was already past its timeout: "The
server did not answer", for a right code only, because a wrong one is refused
before the next frame and a right one waits on the server's database write.
`AC_TYPING_MS` reproduces it against a real server. A gap between pumps longer
than `kSuspendGapMs` is also treated as a suspension rather than silence.

**A login the server has forgotten is logged in again.** AlphaComputer drops a
console it has not heard from for 60 seconds (`PEER_TIMEOUT`), and a console
says nothing while the keyboard applet or HOME has its loop stopped. The join
typed after a minute in the keyboard is then refused, "unknown or expired
session". `ac::Client` takes a refusal while logged in -- one its own repeated
`Auth` does not explain -- as that, starts again from `Hello`, and resends what
was pending once the new `AuthOk` lands. The keep-alive sent on resume is refused
on the same dead token; those refusals arrive before the `Challenge` and are
ignored while the re-login waits on it. Once per `kReloginGuardMs`: a second
expiry straight after is believed. `AC_TYPING_MS=75000` checks it live.

**The login survives its own retransmissions.** The server answers each `Auth`
once -- the first to arrive takes the challenge and gets `AuthOk`, every copy
gets "say hello first" -- and a repeated `Hello` replaces the challenge the
first was answered with. Both used to end the login when an answer took longer
than `kRetryMs`: seen against the real server as a harness that went straight
from connecting to failed. `ac::Client` now ignores the refusals its own copies
earned after an `AuthOk`, and starts a refused handshake that had copies over
once from `Hello`.

The last of those is the only thing that can answer the question a byte vector
cannot: whether the signature this build produces is one the server accepts,
since it is verified by code that is not here.

## Not done

- **NAT-PMP / PCP.** Asking the router to forward a port outright would skip the
  punch where it works. `platform/ctr/network.cpp` already reads
  `NETOPT_ROUTING_TABLE` and pulls out `ROUTING_FLAG_G` entries, so the gateway
  address is a function that already exists.
- **A friend list.** The server has the friendships and no way to say them to a
  console: protocol 2 has no message that asks, and no join is refused on their
  account. Until both exist, two of the three Privacy answers and the Join
  screen's second row are drawn and refused.
- **IPv6.** The wire carries v6 addresses and the decoder handles them;
  `UdpSocket` is v4 only and refuses a v6 destination outright rather than
  failing quietly.
- **Import/Export of a world over the internet.** `net::world_copy` moves a
  whole world in `link::Msg` frames with no flow control of its own, which a
  room's radio carries and a relay with a byte budget does not.
- **Hardware, past the bind.** A console has reached `UdpSocket::open` and been
  refused there; what happens after that on a real one is unknown. Unmeasured:
  whether `PS_GenerateRandomBytes` answers, whether a console with no friend
  account gets a usable device ID, what a punch does behind a real
  carrier-grade NAT, what one scalar multiplication costs on a 268 MHz ARM11 —
  once per login, but nobody has timed it — and whether twenty seconds of
  `Away` covers opening a large world off a slow card.
